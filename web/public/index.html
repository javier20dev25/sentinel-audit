01Cómo usar la consolaDel repositorio al expediente verificable
  1. Confirma la identidad. La consola reutiliza tu sesión de gh; el token nunca llega al navegador. Si no hay sesión, solo verás el aviso y no se enumerarán repositorios.
  2. Elige el repositorio. Haz clic en una tarjeta o actívala con Enter/Espacio. Se abrirá el inventario de PRs abiertos del repositorio.
  3. Selecciona el modo. Lite analiza localmente el diff del PR; Motor local usa el motor Sentinel completo instalado; Pulse envía el checkout fijado a Sentinel Cloud y exige una clave guardada y SENTINEL_CLOUD_URL.
  4. Fija el cambio. El pipeline resuelve el SHA completo del head y clona ese commit; nunca analiza una rama móvil.
  5. Lee la evidencia. Revisa la ruta por etapas, la cobertura real, los hallazgos y los hashes antes de decidir. Si el commit contiene workflows, acciones locales o configuración de Dependabot rastreados y zizmor está disponible, el pipeline agrega su análisis offline como etapa independiente. Un veredicto limpio no demuestra ausencia de defectos.
  6. Archiva y vuelve. Cada ejecución queda en SQLite. Usa Ver resultados en escaneos recientes o el botón de retroceso para regresar sin perder el contexto.
Atajo: Esc cierra el modal o retrocede una pantalla; las tarjetas de repositorio aceptan teclado.
02Requisitos del sistemaQué necesita la consola y qué es opcional
  • CLI: Node.js 20 o posterior.
  • Consola web y SQLite: Node.js 22.5 o posterior (módulo node:sqlite).
  • GitHub: GitHub CLI instalado y con gh auth login completado; se requieren permisos de lectura sobre los repositorios y PRs.
  • Git: necesario para clonar el PR fijado por SHA.

Especialistas opcionales: CodeQL, Semgrep, Trivy, OSV-Scanner, Zizmor, Bandit y ShellCheck. En Windows se instalan desde Herramientas dentro de %USERPROFILE%\.sentinel-audit\tools, sin privilegios de administrador. Semgrep y Bandit requieren Python 3 con el lanzador py; las instalaciones usan wheels binarias. CodeQL exige aceptar sus términos. Las herramientas descargadas no se ejecutan automáticamente.

Fuera de Windows, instala cada especialista desde su proyecto oficial. Sentinel Audit lo reporta como ausente solo cuando no se resuelve por PATH o configuración.

El pipeline v1 conecta CodeQL, Semgrep, Trivy y OSV; además ejecuta Zizmor offline si el commit contiene workflows, acciones locales o configuración de Dependabot. Bandit y ShellCheck siguen en adaptadores heredados y aún no se ejecutan aquí. Que una herramienta esté instalada no significa que haya corrido en este escaneo.
03Integridad del expedienteCómo se sella y qué significa el hash

Cada resultado calcula SHA-256 sobre el cuerpo normalizado del expediente y sobre el diff. El sello del cuerpo permite detectar modificaciones posteriores del JSON; el sello del diff identifica exactamente el cambio analizado.

  • Alcance: el hash prueba integridad del contenido guardado, no autenticidad ni autoría.
  • No es una firma: no sustituye una atestación de GitHub, Sigstore ni una revisión externa.
  • Ampliaciones: al añadir especialistas se recalcula el hash del cuerpo y se conserva el hash del diff original.
  • Persistencia: la base SQLite y los artefactos viven en el perfil local; protégelos como cualquier evidencia.
Si el hash no coincide con el cuerpo mostrado, trata el expediente como no confiable y vuelve a ejecutar el escaneo sobre el SHA fijado.
04Agregar un especialistaContrato de integración y pruebas mínimas
  1. Declara el ejecutable. Añade la entrada en config/tools.json con bin, argv y límites de tiempo/tamaño.
  2. Define la política. En config/policies.json establece cobertura, presupuesto y reglas de enrutamiento por señal.
  3. Implementa el adaptador. Normaliza hallazgos a un esquema estable (severidad, categoría, archivo, línea, evidencia) y conserva la salida cruda como artefacto.
  4. Registra estados explícitos. Distingue AVAILABLE, UNAVAILABLE, FAILED, TIMEOUT, INVALID y CANCELLED; nunca conviertas un fallo en un resultado limpio.
  5. Prueba con fixtures seguros. Añade casos de éxito, ausencia, timeout y error antes de usarlo en repositorios reales.

La ruta debe explicar por qué se ejecutó cada herramienta y qué evidencia produjo; una herramienta no seleccionada por señal no se fuerza.

05Responsabilidad y alcanceLímites del análisis y decisión humana

Sentinel Audit prioriza la revisión: sus detectores pueden producir falsos positivos, falsos negativos y sesgos de cobertura. La persona operadora valida cada hallazgo, decide el reporte y autoriza cualquier cambio o divulgación.

  • Uso autorizado: analiza solo repositorios y PRs sobre los que tengas permiso.
  • Sin garantía: un resultado limpio no certifica seguridad ni cumplimiento.
  • Datos: el análisis Lite es local; Pulse envía el diff al endpoint de Sentinel Cloud configurado. Revisa esa política antes de usarlo con código sensible.
  • Divulgación: coordina con el propietario del proyecto y respeta plazos y canales de reporte.
La consola muestra la cobertura real: interpreta cada veredicto junto con las etapas completadas y las herramientas ausentes.

SENTINEL CLOUD ACCESS

Claves API y Pulse

La clave solo se envía al guardarla y después permanece en el almacén local; el navegador recibe únicamente su máscara e identificador. Pulse usa la clave guardada desde el servidor. Eliminarla aquí no revoca el token en Sentinel Cloud.
